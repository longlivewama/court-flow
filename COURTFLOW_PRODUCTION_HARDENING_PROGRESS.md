## 2026-09-14 (session 3) — Live reminder cron verification (Phase 2 of the follow-up task)

Inspected `infrastructure/cron/index.ts` in full: advisory-lock-serialized cron (key 4021, every 1 min), `sendReminders()` selects confirmed bookings in a ±1-minute window around the 24h/2h mark with a `reminder_XXh_sent_at IS NULL` guard, sends, then marks sent via a race-safe `UPDATE ... WHERE id=$1 AND sentColumn IS NULL` — only after a real send succeeds, inside a per-booking try/catch so one failure doesn't block the rest of the tick.

Live-verified (this dev environment's SMTP points at a fake host, `smtp.example.com`, so real sends genuinely fail — used this to test the failure path for real, and directly tested the DB race-guard for the success path since a real send isn't available):
- **First execution**: created a real confirmed booking (via the API), shifted its `start_time` into the live 24h window via SQL, waited for the actual running cron (no test harness, the real `courtflow_api` container's own scheduler) to tick — confirmed in the container logs it selected the booking, attempted the real SMTP send, got `ENOTFOUND smtp.example.com`, retried 3× internally (exponential backoff, per `email.service.ts`), then logged `"Failed to send booking reminder; will retry next tick"`.
- **Failed send does not falsely mark sent**: `reminder_24h_sent_at` confirmed still `NULL` after the failed attempt — remains eligible for retry, not permanently blocked.
- **Concurrent-worker race safety** (the property the DB guard exists for): fired two genuinely concurrent `UPDATE ... WHERE id=$1 AND reminder_24h_sent_at IS NULL` statements from two separate connections at once — exactly one reported `UPDATE 1`, the other `UPDATE 0`. Postgres's row-level locking on the UPDATE itself serializes this correctly even without an explicit `SELECT ... FOR UPDATE`, so two workers "succeeding" at the exact same instant still produce exactly one durable mark.
- **Already-sent bookings are never re-selected**: reset the booking back into the live 24h window while `reminder_24h_sent_at` was set — waited a full real tick — zero new log lines for this booking, confirming the SELECT-side `IS NULL` guard durably excludes it going forward (this is what makes "at most one successful reminder ever" hold across restarts: the state lives in a DB column, not memory).
- **Worker restart durability**: inherent to the design (DB-column state, not in-memory) — also incidentally exercised for real earlier this session, since the API container was rebuilt/restarted multiple times without any reminder-state loss.
- Test booking fully cleaned up afterward (payments, audit rows, booking row — no ledger entries were created, so no append-only-cleanup blocker this time).
